# OCR demo: reading number plates with PyTorch and Google Cloud

I built this for a one hour hands on workshop called **From Images to Production AI**. The idea is
simple. Take a small OCR problem, build the dataset yourself, train a model, export it and put it
behind an API on Google Cloud that anyone can open in a browser.

The model reads Indian vehicle number plates like `MH 12 AB 1234` and `22 BH 1234 AB`. All plate
images are generated by code, so there are no photos of real cars anywhere in this repo.

```
Dataset  >  Training  >  Model  >  Container  >  Cloud  >  Browser
```

What is used along the way:

* **Python, Pillow and NumPy** to draw the plates and add camera style blur, tilt, shadows and noise
* **PyTorch** to train a small CRNN model (a CNN plus a BiLSTM, trained with CTC loss)
* **ONNX and ONNX Runtime** so the API does not need PyTorch at all
* **FastAPI** for the API and a small HTML page for the demo
* **Docker** for both the training image and the serving image
* **Google Cloud**: Cloud Storage, Vertex AI custom training, Cloud Build, Artifact Registry and Cloud Run

You can run everything on your laptop first and move to Google Cloud when you are ready.

## What is in the repo

```
data/generate.py        draws the plate images, the label is the file name
train/model.py          the CRNN model
train/train.py          training loop, runs the same way locally and on Vertex AI
train/export.py         exports to ONNX, writes model.json, checks ONNX matches PyTorch
train/Dockerfile        training image for Vertex AI
serve/app.py            FastAPI app with ONNX Runtime
serve/static/           demo page
serve/Dockerfile        serving image for Cloud Run
scripts/                Google Cloud scripts, numbered in the order you run them
artifacts/              a model I already trained, handy if you want to skip training
plate.jpg               one sample plate for quick curl tests
Makefile                shortcuts for the local steps
```

## What you need

* Python 3.12 (3.11 should also work)
* `make` and `git`
* Docker, only if you want to run the container locally
* For the cloud part: a Google Cloud project with billing turned on, the `gcloud` CLI and
  Owner or Editor access on the project

No laptop setup? Open **Cloud Shell** from the Google Cloud console (the `>_` icon at the top right).
It already has git, gcloud, Docker and Python.

# Part 1: run it on your laptop

Under most commands I've put the output I got on my machine so you can compare it with yours. Times,
file names and the example plate will be different for you. The Google Cloud outputs in Part 2 are
trimmed and the project name and IDs in them are made up.

## Step 1: get the code

```bash
git clone https://github.com/harsh4870/ocr-demo.git
cd ocr-demo
```

## Step 2: set up Python

```bash
make setup
```

This creates a `.venv` folder and installs everything from `requirements.txt`. It takes a few minutes
the first time because PyTorch is big.

If your Python is not called `python3.12`, pass the right name:

```bash
make setup PYTHON=python3
```

On Linux or Cloud Shell pip may try to download the CUDA build of PyTorch, which is several GB. Press
Ctrl+C and install the CPU build first, then run `make setup` again:

```bash
python3 -m venv .venv
.venv/bin/pip install torch==2.15.0 --index-url https://download.pytorch.org/whl/cpu
make setup PYTHON=python3
```

## Step 3: generate the dataset

```bash
make data
```

You get 20,000 training images and 1,000 validation images in `data/plates/`. It takes around two
minutes. You should see:

```text
.venv/bin/python data/generate.py --out data/plates
train fonts: ['Arial Bold', 'Arial Narrow Bold', 'DIN Condensed Bold', 'Tahoma Bold', 'Verdana Bold'], held-out val font: ['DIN Alternate Bold']
wrote 20000 train + 1000 val images to data/plates
```

That's on a Mac. On Linux or Cloud Shell the font names will be DejaVu or Liberation instead.

Have a look at a few:

```bash
ls data/plates/train | head -5
```

```text
21BH0000GM_16285.jpg
21BH0055HU_11708.jpg
21BH0060XV_13793.jpg
21BH0061JB_9438.jpg
21BH0066UE_16530.jpg
```

Every file is named `<PLATE>_<number>.jpg`, for example `MH12AB1234_7.jpg`. The part before the
underscore is the label, so there is no separate labels file.

A few details worth knowing:

* Plates come in the standard format and the BH series format, in white, yellow and green
* Series letters never use I or O, same as real plates
* Fonts are picked from whatever is installed on your machine. The last font found is used only for
  the validation images, so validation tells you how the model does on a typeface it never saw
  during training

Quick check first. This uses 2,000 images and 2 epochs, so it finishes in about a minute:

```bash
make train-smoke
```

This is what mine printed:

```text

loaded 2000 train / 200 val in 0s, image (1, 32, 128), charset='0123456789ABCDEFGHJKLMNOPQRSTUVWXYZ', device=mps
epoch  1  loss 5.431  val_acc 0.000  (7s)  e.g. 21BH0321GG -> 
epoch  2  loss 3.422  val_acc 0.000  (6s)  e.g. 21BH0321GG -> 
exported artifacts-smoke/model.onnx (4.8 MB), max diff vs torch 9.54e-07
done. best val exact-match accuracy 0.000; artifacts in artifacts-smoke
```

The loss goes down from 5.4 to 3.4. Accuracy is still 0% and the model reads nothing yet. That is normal
for this kind of model, it needs a few epochs before it starts getting full plates right. `device=mps`
means it ran on the Apple GPU. You will see `cpu` or `cuda` on other machines.

You may also see a `UserWarning` from PyTorch about LSTM and batch size during the export. It is
harmless, the export checks itself right after.

Now the real run, 15 epochs on all 20,000 images:

```bash
make train
```

```text
epoch 15  loss 0.001  val_acc 0.990  (45s)  e.g. 21BH0127WN -> 21BH0127WN
exported artifacts/model.onnx (4.8 MB), max diff vs torch 1.03e-05
done. best val exact-match accuracy 0.992; artifacts in artifacts
```

How to read it:

* **epoch** is one full pass over all 20,000 training images. With batch size 64 that is 313 small
  update steps per epoch
* **loss** is how wrong the model is on the training images. Lower is better. It should keep falling
* **val_acc** is the share of the 1,000 validation plates read exactly right, every character. `0.992`
  means 992 of them. These plates use a font the model never saw in training
* **e.g.** shows one validation plate and what the model read for it. Blank in epoch 1 is normal. The
  model starts out predicting "nothing here" everywhere until it learns where the characters are
* Accuracy sits at 0 for two epochs then jumps to 72% in epoch 3. Models trained with CTC loss often
  do this, so don't stop a run early because the first epochs look bad
* Accuracy dips in epochs 6 and 7 even though the loss keeps falling. The learning rate is near its
  peak around there, so the model moves around a bit. It settles once the rate comes down
* The best epoch gets saved, not the last one. Here that was epoch 9 with 99.2%
* Tiny loss with low val_acc would mean the model memorised the training plates without learning to
  read. Tiny loss with high val_acc, like here, is what you want

The same numbers are saved in `artifacts/metrics.json` if you want to plot them:

```json
{
  "best_val_acc": 0.992,
  "history": [
    {"epoch": 1, "loss": 4.285, "val_acc": 0.0},
    {"epoch": 2, "loss": 3.139, "val_acc": 0.0},
    {"epoch": 3, "loss": 1.249, "val_acc": 0.721}
  ]
}
```

I've shortened the history there. The real file has all 15 epochs.

On an Apple Silicon Mac this took about 45 seconds per epoch. On a plain CPU expect roughly twice
that. When it finishes you will find these in `artifacts/`:

```
model.pt        the PyTorch checkpoint
model.onnx      the exported model, about 4.8 MB
model.json      charset and preprocessing values the API needs
metrics.json    loss and accuracy for every epoch
```

Training settings, if you want to change them: batch size 64, AdamW with a one cycle learning rate
schedule peaking at 0.001, gradient clipping at 5. You can pass `--epochs`, `--batch` and `--lr` to
`train/train.py`.

Don't want to wait? Skip this step. The repo already has a trained model in `artifacts/`.

## Step 5: export to ONNX

Training already exports at the end. To do it again by hand:

```bash
make export
```

It prints the largest difference between PyTorch and ONNX Runtime outputs on the same input:

```text
exported ../artifacts/model.onnx (4.8 MB), max diff vs torch 1.38e-05
```

Anything around `1e-05` is fine. That is a difference in the fifth decimal place, far too small to
change a single letter. If it is ever above `1e-3` the export stops with an error. A
`DeprecationWarning` about the legacy TorchScript exporter above that line is also fine.

## Step 6: run the API

```bash
make serve
```

```text
INFO:     Will watch for changes in these directories: ['/Users/you/ocr-demo/serve']
INFO:     Uvicorn running on http://127.0.0.1:8080 (Press CTRL+C to quit)
INFO:     Started server process [31501]
INFO:     Waiting for application startup.
INFO:     Application startup complete.
```

Open http://localhost:8080 and click **Read another plate**. The page picks a random validation
plate, sends it to the model and shows what it read.

In a second terminal, send an image yourself:

```bash
curl -F file=@plate.jpg localhost:8080/predict
```

You will get back something like this:

```json
{"text": "21BH0680KD", "plate": "21 BH 0680 KD", "valid_format": true,
 "confidence": 0.9536, "needs_review": false, "latency_ms": 3.4}
```

`needs_review` turns true when the reading does not match a valid plate format or when the confidence
is below 0.9. Those are the cases you would want a person to look at. `latency_ms` will jump around
on a laptop. The first request is always the slowest.

Two more checks worth doing:

```bash
curl localhost:8080/healthz
```

```text
{"status":"ok","model_version":"dev","charset_size":35}
```

```bash
curl -F file=@Makefile localhost:8080/predict
```

```text
{"detail":"not a valid image"}
```

That second one is on purpose. Sending a file that is not an image should give a clean 400 error and
not crash the server.

All scripts read their settings from `scripts/config.sh`. By default they use your current gcloud
project, region `us-central1`, a bucket called `<project>-ocr-workshop` and a Cloud Run service called

## Step 11: train on Vertex AI

```bash
./scripts/03_train_vertex.sh
```

The script builds the training image with Cloud Build, pushes it to Artifact Registry and starts a
Vertex AI custom job on an `n1-standard-4` machine with one NVIDIA T4 GPU. It then streams the logs.
Vertex AI mounts your bucket at `/gcs/<bucket>`, so `train.py` reads and writes it like a normal folder.

The output comes in three parts. First Cloud Build builds the training image:

```text
Creating temporary archive of 5 file(s) totalling 6.2 KiB before compression.
Uploading tarball of [train] to [gs://my-project_cloudbuild/source/1763791502.4-ab12cd34.tgz]
...
DONE
```

Then the job is created:

```text
Job: projects/123456789012/locations/us-central1/customJobs/4517283941023744000
Console: https://console.cloud.google.com/vertex-ai/training/custom-jobs?project=my-project
```

Then the training logs stream in. It is the same log you saw on your laptop, with a timestamp and
`workerpool0-0` (the machine running it) in front of each line:

```text
INFO  2026-11-22 10:15:02 +0530  service        Waiting for job to be provisioned.
INFO  2026-11-22 10:19:40 +0530  service        Job is running.
INFO  2026-11-22 10:21:08 +0530  workerpool0-0  loaded 20000 train / 1000 val in 41s, image (1, 32, 128), charset='0123456789ABCDEFGHJKLMNOPQRSTUVWXYZ', device=cuda
INFO  2026-11-22 10:21:26 +0530  workerpool0-0  epoch  1  loss 4.301  val_acc 0.000  (18s)  e.g. 21BH0127WN -> 
INFO  2026-11-22 10:21:43 +0530  workerpool0-0  epoch  2  loss 3.152  val_acc 0.000  (17s)  e.g. 21BH0127WN -> 21
INFO  2026-11-22 10:22:00 +0530  workerpool0-0  epoch  3  loss 1.307  val_acc 0.704  (17s)  e.g. 21BH0127WN -> 21BH0127WN

INFO  2026-11-22 10:25:16 +0530  workerpool0-0  epoch 15  loss 0.001  val_acc 0.990  (17s)  e.g. 21BH0127WN -> 21BH0127WN
INFO  2026-11-22 10:25:19 +0530  workerpool0-0  done. best val exact-match accuracy 0.991; artifacts in /gcs/my-project-ocr-workshop/models/run-20261122-101455
INFO  2026-11-22 10:26:02 +0530  service        Job completed successfully.
Model artifacts: gs://my-project-ocr-workshop/models/run-20261122-101455/
```

A few things to notice:

* Expect around 5 minutes of `Waiting for job to be provisioned`. Google is finding a machine with a
  GPU and pulling your image. Nothing is wrong
* `device=cuda` means the GPU is being used. With `ACCELERATOR=none` you will see `device=cpu` and
  each epoch takes a lot longer
* Loading takes longer than on a laptop because the 20,000 images are read from Cloud Storage
* Your accuracy will not match mine to the last digit. Training is random. Anything around 98% to 99%
  is a good run
* You can close the terminal while it streams. The job keeps running in the cloud

New projects often have no GPU quota. If the job fails with a quota error, train on CPU instead:

```bash
ACCELERATOR=none ./scripts/03_train_vertex.sh
```

# Settings you can change

API (`serve/app.py`), set as environment variables:

* `MODEL_DIR` folder with `model.onnx` and `model.json`, default `serve/model`
* `SAMPLES_DIR` folder with plates for the demo button, default `serve/model/samples`
* `REVIEW_BELOW` confidence under which `needs_review` is true, default `0.9`
* `ORT_THREADS` ONNX Runtime threads, default `1`
* `MODEL_VERSION` shown on `/healthz`

Scripts:

* `PROJECT_ID`, `REGION`, `BUCKET`, `REPO`, `SERVICE` override the defaults in `scripts/config.sh`
* `EPOCHS` and `ACCELERATOR` for `03_train_vertex.sh`
* `MODEL_SRC` and `DATA_DIR` for `04_deploy.sh`

# API

* `POST /predict` upload an image as `file`, returns the reading
* `GET /sample` a random validation plate with the model's answer, used by the demo page
* `GET /healthz` status, model version and charset size
* `GET /` the demo page

Uploads over 2 MB or larger than 4 megapixels get a 413. Anything that is not an image gets a 400.

# Numbers from my run

* 99.2% exact match accuracy on 1,000 validation plates in a font the model never trained on
* 992 out of 1,000 read correctly through the API container
* About 3.4 ms per image on 1 CPU, 4 ms at the 95th percentile
* Model file 4.8 MB with 1.19 million parameters
* Serving image 118 MB, while the PyTorch training base image is close to 4 GB

One small thing I learned along the way: ONNX Runtime starts one thread per CPU core it can see. With
only one real CPU those threads get in each other's way and the slowest requests went up to 188 ms.
Setting it to a single thread brought that down to 4 ms. That is why `ORT_THREADS` defaults to 1.

# When something goes wrong

* **`Set a project first`** run `gcloud config set project YOUR_PROJECT_ID`
* **GPU quota error on Vertex AI** use `ACCELERATOR=none ./scripts/03_train_vertex.sh` or ask for T4 quota
  in `us-central1` a few days before you need it
* **`PERMISSION_DENIED` from Cloud Build** you need Owner or Editor on the project
* **Vertex AI job cannot read the bucket** keep the bucket in the same project as the job
* **`/sample` returns 404** there were no demo plates to copy. Run `make data` and deploy again
* **Docker hangs while pulling images on macOS** point `DOCKER_CONFIG` to a folder whose `config.json` is
  just `{}` and try again
* **Wrong text with high confidence** check that `model.json` belongs to the same model as `model.onnx`
* **Good on the demo, bad on your own photos** expected. The model reads tight plate crops of
  generated plates. Real use needs a plate detector in front of it and some real labelled crops for
  fine tuning
* **First request on Cloud Run is slow** that is a cold start. `--min-instances=1` avoids it but you pay
  for the idle instance

# A note on plates and privacy

A plate number points to a real person, so treat it as personal data. If you build something like
this for real, decide what it is for first, keep as little as you can for as short as you can and
have a person check before anything that affects someone, like a fine or a gate that stays closed.
